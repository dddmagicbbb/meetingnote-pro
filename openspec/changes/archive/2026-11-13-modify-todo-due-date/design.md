# Design

## Context

- 지금 기한은 `todos.due_text` 글자 한 칸뿐이다. Gemini 가 뽑은 글자(「다음 주 금요일」)나 사람이 넣은 글자를 그대로 저장한다
- 기한 지남은 `frontend/api.js` 의 `isLate` 가 「어제 · 지난주 · 지난달」 세 글자만 보고 판정한다
- 칸반(`todos.html`)은 화면에서 다시 정렬하는데 기준이 due_text 글자 순이다
- DB 는 시작 때 `create_all` 로만 만든다. 이미 있는 테이블에 열을 더하지 않으므로 이관을 따로 해야 한다
- 동기는 proposal.md - Why, 요구사항은 `specs/todo` · `specs/meeting` 을 본다

## Goals / Non-Goals

**Goals:**
- 같은 글자 · 같은 기준일이면 언제 돌려도 같은 날짜가 나온다 (정해진 규칙, 외부 호출 없음)
- 원래 글자는 절대 잃지 않는다
- 이미 쌓인 로컬 데이터도 서버를 다시 띄우면 날짜가 채워진다

**Non-Goals:**
- 날짜 고르기 달력, 날짜를 직접 보내는 API (`due_date` 는 응답 전용)
- Alembic 도입 - 열 하나라 시작 시 이관 함수로 처리하고, 배포 change 에서 이관 도구를 정한다

## Decisions

### 1. 변환은 서버의 정해진 규칙 (`backend/duedate.py`)

- `parse_due(text: str, base: date) -> date | None` 하나만 둔다. 저장 · 수정 · 이관이 모두 이 함수를 쓴다
- 대안: Gemini 가 날짜까지 뽑게 하기 → 실행마다 결과가 달라질 수 있고 테스트가 어렵다. 직접 등록 · 수정 경로에는 Gemini 가 없어 어차피 규칙이 필요하다

글자 다듬기: 공백을 지우고 대조한다. 「N일 뒤 · 후 · 안 · 이내」 는 먼저 상대 날짜(B+N)로 본 뒤, 나머지는 끝의 「까지 · 안에 · 안 · 중 · 내 · 이내 · 에 · 전」 을 떼고 대조한다 (「다음 주까지」 와 「다음 주」 는 같은 규칙으로 7일 뒤, 「15일까지」 는 15일).

변환표 (기준일 = B, 주는 월요일 시작, W(B) = B 가 속한 주의 월요일):

| 글자 (다듬은 뒤) | 날짜 |
|---|---|
| 오늘 · 당일 | B |
| 내일 | B+1 |
| 모레 | B+2 |
| 어제 | B-1 |
| N일 뒤 · N일 후 · N일 안 · N일 이내 | B+N |
| 다음 주 · 다음주 (뒤에 요일 없음) | B+7 |
| 이번 주 · 이번주 · 금주 (뒤에 요일 없음) | W(B) 의 금요일 |
| 이번 주 X요일 | W(B) 의 X요일 |
| 다음 주 X요일 | W(B)+7 의 X요일 |
| 다다음 주 X요일 | W(B)+14 의 X요일 |
| X요일 (주 표시 없음) | B 다음 날부터 가장 가까운 X요일 |
| M월 D일 | B 의 해의 M/D. 그날이 B 보다 앞이면 다음 해 |
| 이번 달 D일 · D일 · D일까지 | B 의 달 D일. 「D일」 만 쓴 경우 그날이 B 보다 앞이면 다음 달 |
| 다음 달 D일 | B 다음 달 D일 |
| 이번 달 말 · 월말 | B 의 달 마지막 날 |
| 다음 달 말 | B 다음 달 마지막 날 |
| YYYY-MM-DD · M/D | 그 날짜 (M/D 는 「M월 D일」 규칙) |
| 그 밖 (다음 분기 · 곧 · 지난주 · 지난달 · 빈 글자 · 없는 날짜 2월 30일 …) | None |

- 「지난주 · 지난달」 은 과거 어느 날인지 하나로 정해지지 않아 None 이다. 기존 붉은 띠 규칙은 날짜 비교로 대체된다
- 요일은 「월 · 화 · 수 · 목 · 금 · 토 · 일」 + 「요일」 이 붙은 꼴만 받는다 (「금」 한 글자는 받지 않음)

### 2. 기준일 - 한국 날짜

- 회의록 할 일: `met_at`(UTC) 을 UTC+9 로 옮긴 날짜. 직접 등록: 등록 시각(`created_at`)의 UTC+9 날짜
- 한국은 서머타임이 없어 고정 +9 시간으로 계산한다 (`zoneinfo` 는 윈도우에서 `tzdata` 패키지가 따로 필요해 쓰지 않음)
- 대안: 보는 사람 브라우저 시간대 → 같은 할 일이 사람마다 다른 날짜가 되어 버림

### 3. 기한 글자 수정 시 다시 계산

- `PUT /api/todos/{id}` 에 `due_text` 가 오면 원래 기준일로 다시 계산한다. 회의 할 일이면 회의의 `met_at`, 직접 등록이면 `created_at`
- 회의록의 `met_at` 을 나중에 고쳐도(`PUT /api/meetings/{id}`) 딸린 할 일 날짜는 다시 계산하지 않는다 - 정의서 7-3 「본문을 고쳐도 뽑아 둔 세 항목은 그대로」 와 같은 원칙

### 4. 저장 모양과 이관

- `todos.due_date` DATE NULL. 응답에서는 `YYYY-MM-DD` 문자열
- 시작 시 `create_all` 다음에 `migrate()`: `inspect(engine)` 로 열이 없으면 `ALTER TABLE todos ADD COLUMN due_date DATE`, 이어서 `due_date IS NULL AND due_text <> ''` 인 행을 규칙으로 채운다. 여러 번 돌려도 같은 결과
- SQLite · Postgres 모두 같은 SQL 로 동작한다

### 5. 화면

- `api.js` 의 `isLate(todo)` → `todo.status !== "DONE" && todo.due_date && todo.due_date < 오늘(브라우저 현지 날짜 YYYY-MM-DD)`. `LATE_WORDS` 는 지운다
- `FMT.due(todo)` 를 더한다 → 「10월 2일 (금)」. 칩에는 날짜를 굵게, 원래 글자를 옅게 붙인다 (`text-ink-3 dark:text-dim`, publish 에 있는 클래스). 날짜가 없으면 글자, 둘 다 없으면 「미정」
- 칸반 화면 정렬은 서버와 같게 status → due_date(빈 값 뒤) → due_text
- 상세 화면 기한 입력칸은 그대로 글자를 고치고, 저장 응답의 날짜를 칸 옆에 보인다
- 새 색 · 새 클래스 조합을 만들지 않는다

## Risks / Trade-offs

- [규칙에 없는 표현이 자주 나옴] → None 으로 두고 글자는 남기므로 정보 손실은 없다. 자주 나오는 표현은 변환표에 행을 더하는 작은 change 로 늘린다
- [「X요일」 만 쓴 경우 이번 주인지 다음 주인지 사람마다 다르게 이해] → 「기준일 다음 날부터 가장 가까운 X요일」 로 고정하고 화면에 날짜를 같이 보여 사람이 바로 알아채게 한다
- [시작 시 이관이 DB 를 바꿈] → 열 추가와 빈 칸 채우기만 하고 기존 값은 건드리지 않는다. 로컬 DB 는 git 밖이라 문제가 생기면 지우고 다시 만들 수 있다
- [브라우저 시간대가 한국이 아닌 사람] → 지남 판정은 보는 사람의 오늘 기준이라 하루 차이가 날 수 있다. 사용자 전제(한국어 사용자)상 받아들인다

## Migration Plan

- 배포 전 단계라 로컬만 해당한다. 서버를 다시 띄우면 `migrate()` 가 열을 더하고 채운다
- 되돌리기: 코드만 되돌리면 남은 `due_date` 열은 쓰이지 않을 뿐 동작에 영향이 없다
